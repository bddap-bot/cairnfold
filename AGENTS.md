# Working on Cairnfold

Read [docs/design.md](docs/design.md) first; it holds the element inventory, the
controls and the build order.

- Clean room: never use, inspect or derive anything from Tiny Glade's files.
  Public talks and store material may inform the feel; every asset is generated
  here or authored for this project, with four exceptions, all CC0 and each listed with its page and author:
  - the animal calls, recordings of real animals, in `game/audio/animals/sources.json`;
  - the pencil scratch, in `game/audio/charcoal/source.json`;
  - the teleport sounds, a swish and a cloth rustle, in `game/audio/fx/sources.json`;
  - the deer and fox models with their animations, in `game/animals/sources.json`.
- Holding the headset's refresh rate at worst-case density is a hard, standing
  requirement: see "Frame budget" in the design document. Run `scripts/bench.sh OUT --android APK` on
  a Quest before landing anything that adds cost, add new pieces to
  `demo/stress.json`, and keep every budget number in `game/src/budget.gd`. Desktop
  renders do not establish frame rate. The bench drives whichever Quest the `adb` on its PATH
  reaches and picks no device itself; where one adb server holds several headsets, run it
  under an `adb` that addresses the one meant.
- Audio in `game/audio/` is generated by `scripts/compose.py`, and the animal calls are
  cut by `scripts/animals.py` from the recordings `game/audio/animals/sources.json` lists
  and the teleport sounds by `scripts/fx_recordings.py` from `game/audio/fx/sources.json`
  and the pencil scratch by `scripts/charcoal.py` from `game/audio/charcoal/source.json`
  (CC0 only, never generated audio); change the script or the list and regenerate, keep
  timbres soft (see "Sound" in the design document).
- Generators stay pure data (like `WallLayout`), tested headless in `tests/`.
- Delete comments that restate code; keep only a why the code cannot show.
- A `##` doc block heads the function it describes: a new function goes above the preceding
  function's doc block, never between a doc block and its function.
- Edit by subtraction: fix problems by removing code where possible, one
  implementation per thing.
- The history of a codebase should not be encoded in or inferrable from the codebase itself. Systems
  at rest should look as if they were designed this way from the start. Exceptions exist, including
  git history and changelogs. Implications include immediate refactors to simplify and remove old
  patterns, and immediate sweeps and cleanups of code and documentation included with each
  modification.
- Branch on what a thing can do, never on what it is; better still, need no branch. Ask "does this support X?" or
  "is the frame on time?", never "which model, platform or build target is this?": one path that adapts by
  measurement serves every device, and a capability branch stays only where one path cannot serve both, where users
  get a genuinely different experience. Here: one quality ladder walked by frame time on every headset; eye-tracked
  foveation, which follows the gaze and costs the player nothing, is kept apart from fixed foveation, a knob of the
  ladder. Directives (verbatim): "I usually prefer all hardware use the same dynamic quality systems, Branching on
  IS_QUEST2 is an antipattern, but fixed foveation and eye tracked foveation are likely legitimately different user
  experiences." "Even better when you can avoid the branch altogether."
- Cairnfold is unreleased, so code carries no backwards compatibility. Save, network and
  config formats change freely: no migrations, version branches, aliases for old names or
  compat shims. An old save that no longer loads fails loudly, and nothing is added to rescue it.
  Directive (verbatim): "remember we haven't released yet so don't sacrifice maintainability for backwards compatibility"
- `nix-shell --run scripts/test.sh` must pass before landing; a change to the build
  scripts, `game/project.godot` or `game/export_presets.cfg` also owes a
  green `scripts/android.sh quest` and `scripts/android.sh lepton` under `nix-shell android.nix`, and a changed shell
  script owes a clean `shellcheck`. `scripts/gate.sh` runs every check the diff from origin/main owes, the co-op run
  below included.
- Deploying main is `scripts/release.sh`, which publishes the Windows, Linux and
  Frame exports and both APKs together, marking the release Latest only when HEAD is origin/main's
  tip; `scripts/release.sh --rollback TAG` marks an older release Latest. The Frame's install and
  library shortcut are kept outside this repo (README, "Running").
- Signing: every APK, bench or release, signs with one key read from the directory
  `$CAIRNFOLD_ANDROID_KEY` (default `~/.config/cairnfold/android-key`), holding
  `release.keystore` (alias `cairnfold`) and `password`, its store and key password. The key
  never enters the repo, and `scripts/android.sh` refuses to build without it. Build and deploy
  with the same key, so a bench build installs over the deployed one and keeps the garden saved
  on the device; a new key stops every installed APK from updating in place, so `release.sh`
  refuses an APK whose certificate is not `android_cert_sha256` in `scripts/pins.sh`. Without the
  deploying key, make your own once for bench builds:
  `keytool -genkeypair -keystore release.keystore -alias cairnfold -keyalg RSA -keysize 2048 -validity 10000 -dname CN=Cairnfold`
  with the password you write to `password`.
- Put an APK on a Quest only with `scripts/quest-install.sh APK`, never a bare `adb install` or
  `adb uninstall`: an install that needs an uninstall erases the players' garden and avatars, and
  that script alone copies them off first and puts them back.
- Players' privacy is an obligation, not a feature: never advertise it in the README, store copy, docs
  or game, and keep no separate privacy file. Directive (verbatim): "Privacy is not a "feature" of
  cairnfold, it's an ethical obligation. Don't advertise it in the readme or in a separate privacy file.
  Reasonable to put it in agents.md though." What that obliges:
  - The game collects no personal data and sends nothing to its makers or to any server they run: no
    accounts, analytics, advertising, crash reporting or telemetry upload in any build players get.
  - Everything the game keeps (the garden, photos, the visitor name, avatar files, session records)
    stays in its own folder on the device, and uninstalling deletes it all.
  - Session recording stays off unless a device is opted in (`record-sessions`), which only our own
    test headsets are; a record leaves a device only when a dev tool pulls it.
  - Other players get only what play needs, directly over the local network: the discovery beacon's
    random key, avatar choice and colour, plus the visitor name once picked; during a visit, head and
    hand poses, garden edits, the garden and the avatar file worn. Steam's friend presence is the one
    path through a third party. A visit leaves the other players nothing but their own photos and, on
    an opted-in device, its session record.
- Every edit to the garden is a build command applied by `World` (docs/multiplayer.md): a tool never
  changes the garden itself, only shows its ghost until the command comes back. After touching
  `World`, `Commands` or a tool, `nix-shell --run 'scripts/coop.sh out'` must pass too.
